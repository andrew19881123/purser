# Data Plane Configuration

Purser v0.5 introduces a first-class **Control Plane / Data Plane (CP/DP) split**.
The Control Plane is the management authority (registry, scheduler, PKI, REST API);
the Data Plane is the inference execution layer (Agents running on your GPU nodes,
each backed by a real inference engine such as llama.cpp).

## Architecture

```
┌─────────────── Control Plane ──────────────────┐
│  Registry · Scheduler · PKI · REST API         │
│  API Gateway (OpenAI + Anthropic endpoints)     │
└─────────────────────┬──────────────────────────┘
                      │  gRPC/mTLS  (enroll · heartbeat · plan)
          ────────────┼─────────────────────────────
                      │
┌─────────────── Data Plane ─────────────────────┐
│  Agent Node 1          Agent Node 2             │
│  llama.cpp (stage 0)   llama.cpp (stage 1)      │
│  activations ◀────────────────────────▶         │
└────────────────────────────────────────────────┘
```

A single Control Plane can manage multiple Data Planes (e.g. production,
development, edge). Each Data Plane is identified by an `id` and a `gatewayUrl`.

## Engine backend

Each Agent selects an inference engine via `PURSER_ENGINE_BACKEND`:

| Value | Description |
|---|---|
| `llamacpp` | Real GPU inference via llama.cpp (production default) |
| `mock` | Canned responses, no GPU (demo and CI only) |

The Helm chart and agent packages default to `llamacpp`. The Docker Compose demo
stack explicitly sets `mock` so it runs without a GPU.

!!! warning "Never use mock in production"
    The `mock` backend fabricates token streams and metrics. It is suitable only
    for UI smoke-tests and CI pipelines where no real GPU is available.

To override on a per-agent basis, set the environment variable directly on the
agent systemd unit:

```ini
# /etc/purser/agent.env (sourced by the systemd unit)
PURSER_ENGINE_BACKEND=llamacpp
```

Or via the Helm chart:

```bash
helm upgrade purser oci://ghcr.io/andrew19881123/charts/purser \
  --set agent.engineBackend=llamacpp
```

## Registering a Data Plane

### Option A: Pre-register at install time (Helm)

Use `controlPlane.dataplanes[]` in your Helm values. Each entry is seeded
idempotently at Control Plane startup — existing records are never overwritten:

```yaml
# values.yaml
controlPlane:
  dataplanes:
    - id: dp-prod
      name: "Production Data Plane"
      tier: production
      gatewayUrl: "https://ai.acme.com"
    - id: dp-dev
      name: "Development Data Plane"
      tier: development
      gatewayUrl: "https://ai-dev.acme.com"
```

```bash
helm install purser oci://ghcr.io/andrew19881123/charts/purser \
  --namespace purser --create-namespace \
  -f values.yaml
```

Join tokens are generated by the Control Plane and stored as Kubernetes Secrets:

```
<release>-control-plane-dp-<id>-token
```

Remote Gateways read the token from this Secret at startup.

### Option B: Register via the REST API

```bash
curl -X POST https://purser.example.com/api/v1/dataplanes \
  -H "Authorization: Bearer <admin-token>" \
  -H "Content-Type: application/json" \
  -d '{
    "id": "dp-prod",
    "name": "Production Data Plane",
    "tier": "production",
    "gatewayUrl": "https://ai.acme.com"
  }'
```

Retrieve the join token from the response; securely distribute it to the
Gateway running in the Data Plane.

### Option C: Register via the Operator UI

Navigate to **Settings → Data Planes → Register new** and fill in the form.
The join token is shown once — copy it before closing the dialog.

## Multi-Data-Plane deployment example

A typical enterprise topology has separate Data Planes for production and
non-production environments:

```bash
# Install with two pre-registered DPs
helm install purser oci://ghcr.io/andrew19881123/charts/purser \
  --namespace purser --create-namespace \
  --set controlPlane.service.type=LoadBalancer \
  --set "controlPlane.dataplanes[0].id=dp-prod" \
  --set "controlPlane.dataplanes[0].name=Production DP" \
  --set "controlPlane.dataplanes[0].tier=production" \
  --set "controlPlane.dataplanes[0].gatewayUrl=https://ai.acme.com" \
  --set "controlPlane.dataplanes[1].id=dp-dev" \
  --set "controlPlane.dataplanes[1].name=Development DP" \
  --set "controlPlane.dataplanes[1].tier=development" \
  --set "controlPlane.dataplanes[1].gatewayUrl=https://ai-dev.acme.com"
```

Models are deployed to a specific Data Plane using the `dataplaneId` field in
the deployment request. Requests routed through the production Gateway are
served only from production Data Plane agents.

## Data Plane fields reference

| Field | Required | Description |
|---|---|---|
| `id` | Yes | Unique identifier (used in join tokens and routing). |
| `name` | Yes | Human-readable display name. |
| `tier` | No | Logical tier label (`production`, `development`, `edge`, …). |
| `gatewayUrl` | Yes | Base URL of the API Gateway serving this Data Plane. |
